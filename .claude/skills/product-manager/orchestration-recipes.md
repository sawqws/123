# Orchestration Recipes — мультиагентные бригады для PM

> Читается на **Этапе C** (Step 6), после того как пользователь выбрал НАБОР скиллов.
> Здесь: как из набора скиллов собрать **бригаду агентов**, какой движок взять, и готовые «составы» под тип задачи.
>
> Базовый канон качества:
> **дизайн-агенты ПЕРВЫМИ (визуал вперёд) → реализация по слайсам → на каждом слайсе параллельно рефактор + автотесты + ревью → адаптивный супервайзер решает, нужен ли доп. проход.**

---

## 1. Соло или бригада? (эвристика масштаба)

PM **сам оценивает масштаб**, но финальный выбор всегда за пользователем.

| Признак | → Соло | → Бригада |
|---|---|---|
| Кол-во скиллов в наборе | 1-2 | 3+ |
| Слайсы / независимые куски | 1 | 2+ можно параллелить |
| Нужен контроль качества (тесты/ревью/рефактор) | нет | да |
| Дизайн + билд в одной задаче | — | да (дизайн вперёд) |
| Тип | мелкая правка, один артефакт | фича, кампания, ресёрч, редизайн |
| Риск/цена ошибки | низкий | высокий → адверсариальная проверка |

**Дефолт:** мелкое → советуй соло (Этап C сворачивается в простой хендофф Step 7). Крупное/многослайсовое/«дизайн+билд»/контент-кампания/ресёрч → советуй бригаду. **Никогда не строй бригаду ради бригады** — если задача соло, честно скажи об этом.

---

## 2. Движок — ГИБРИД (канон)

PM = **мета-супервайзер**. Он не отдаёт всю задачу в один чёрный ящик — он ведёт её по фазам, читает результат каждой и решает следующую.

- **Тяжёлые параллельные фазы** (N строителей, пачка ревьюеров, fan-out поиск, адверсариальная верификация, loop-until-dry) → **`Workflow`**. Один well-scoped fan-out на фазу. Выбор пользователем «бригада» на Step 6 = его **явный opt-in** на Workflow.
- **Лёгкие / последовательные / интерактивные шаги** (один дизайн-проход, быстрый рефактор, проверка гипотезы) → **`Agent`**-субагенты прямо в диалоге — пользователь видит каждый шаг.
- **Между фазами** решает САМ PM (главный цикл): прочитал вывод Workflow → «дизайн поехал, добавлю ещё проход» / «0 багов → пропускаю верификацию» / «готово».

**Правило выбора движка по фазе:**
- фаза порождает ≥3 параллельных агентов и результаты нужны разом → Workflow `parallel`;
- многостадийная работа над списком элементов (слайс: build→test→review) → Workflow `pipeline`;
- один-два агента, нужен глаз пользователя по ходу → `Agent` в диалоге.

**Изоляция:** если строители параллельно правят ОДНИ и те же файлы → `isolation: 'worktree'`. Если каждый в своём модуле — обычные агенты.

---

## 3. Роли в бригаде (канонический состав)

Маппинг **выбранных скиллов** на роли. Не все роли обязательны — бери под задачу.

| Роль | Что делает | Типовые скиллы |
|---|---|---|
| 🎨 **Дизайн** (первым) | визуал/IA/паттерн до кода | `ui-ux-pro-max` 🔒 → `hallmark` 🔒 → `frontend-design` |
| 🔨 **Строители** | пишут код по слайсам, параллельно | `eng-incremental-implementation`, `eng-frontend-ui-engineering`, стек-скиллы `ag-*`, `supabase`, `fastapi-pro` |
| 🧪 **Тесты** | автотесты на слайс | `eng-test-driven-development`, `ag-playwright-skill`, `eng-browser-testing-with-devtools` |
| ♻️ **Рефактор** | чистит сразу после билда | `eng-code-simplification`, `simplify`, `ag-clean-code`, `lab-refactoring-kit-v2` |
| ✅ **Ревью** | код-ревью / безопасность | `code-review`, `eng-code-review-and-quality`, `eng-security-and-hardening`, `ag-*-security-coder`, `security-review` |
| 🧭 **Супервайзер** | адаптивный надзор (см. §4) | сам PM + `eng-architect`/`ar-architect-review` по запросу |

**Порядок жёсткий:** дизайн → билд → (на каждом слайсе) тест+рефактор+ревью. Дизайн НИКОГДА не после кода.

---

## 4. Адаптивный супервайзер (ключевая фича)

Это «человек, который смотрит на код и думает — а может, добавить ещё дизайн-скилл». Реализуется как **критик-проход между фазами** (Workflow completeness-critic ИЛИ отдельный Agent), который возвращает структурный вердикт:

```
{ verdict: "ok" | "needs_more",
  add_passes: ["design" | "security" | "perf" | "refactor" | "tests"],
  why: "..." }
```

PM читает вердикт и **доращивает бригаду на лету**:
- `add_passes: ["design"]` → ещё проход `ui-ux-pro-max`/`hallmark` (UI поехал, несогласованность);
- `["security"]` → `eng-security-and-hardening` / `ag-backend-security-coder`;
- `["perf"]` → `eng-performance-optimization` / `ag-performance-optimizer`;
- `["tests"]` → добить покрытие `eng-test-driven-development`.

**Loop-until-clean:** повторяй цикл build→critic пока critic не вернёт `ok` ДВА раунда подряд (или пока пользователь не скажет «стоп»). Не зацикливайся молча — логируй каждый доп. проход.

## 5. Готовые бригады (recipes)

### Recipe A — Код / билд-фича (фичи, приложения, сервисы)
```
Фаза 1 ДИЗАЙН (если есть UI):  ui-ux-pro-max → hallmark → frontend-design   [Agent, последовательно]
Фаза 2 ПЛАН:                   eng-planning-and-task-breakdown → слайсы     [Agent]
Фаза 3 BUILD+QA (pipeline):    каждый слайс: build → tests → refactor → review   [Workflow pipeline, worktree если конфликт файлов]
Фаза 4 КРИТИК:                 completeness-critic → add_passes?            [Agent/Workflow]
   ↑ если needs_more — вернуться в нужную фазу (loop-until-clean ×2)
Фаза 5 СБОРКА:                 PM сшивает, verify, прогон
```
Движок: Фаза 3 — Workflow `pipeline` (слайс = элемент, стадии = build/test/refactor/review). Остальное — Agent.

### Recipe B — Дизайн + UI (лендинг, экран, редизайн)
```
ui-ux-pro-max (--design-system --persist <проект>)  →  hallmark (study/audit/redesign)  →  frontend-design (код)  →  ревью уникальности (hallmark self-critique 6 осей)
```
Канон пользователя: mandatory-порядок, дизайн вперёд, hallmark между системой и кодом. Чаще соло-цепочка, бригада — если несколько экранов параллельно.

### Recipe C — Контент-кампания (посты/видео/Reels под канал)
```
Фаза 1 РЕСЁРЧ:    mkt-autoresearch / deep-research                 [Workflow fan-out]
Фаза 2 КРАФТ:     N вариантов параллельно (content-strategy, mkt-short-form-pipeline, mkt-x-longform-post)  [Workflow parallel]
Фаза 3 ОЦЕНКА:    mkt-content-eval / judge-панель → лучший          [Workflow parallel judges]
Фаза 4 УПАКОВКА:  адаптация под TG/IG/Threads/X                     [Agent]
```

### Recipe D — Ресёрч / анализ
```
fan-out поиск (несколько углов) → дедуп → адверсариальная верификация (N скептиков на claim) → синтез с цитатами
```
Движок: целиком Workflow (multi-modal sweep + verify + synthesize). Это классический deep-research-паттерн.

### Recipe E — Соло (мелкая задача)
Никакой бригады. Один агент применяет 1-2 скилла по хендоффу (Step 7). Этап C = одна строка «тут бригада избыточна, иду соло».

---

## 6. Что передать в бригаду на хендоффе

При запуске КАЖДОГО агента/Workflow передавай:
1. **Распарсенный контекст задачи** (с Этапа A) — чтобы не переспрашивал;
2. **Точную команду/режим скилла** (из `commands-cheatsheet.md`);
3. **Его роль и границы** («ты строитель слайса X, не трогай Y»);
4. **Принципы пользователя из `favorites.md`** (если заполнены) — стиль, ограничения, табу;
5. Для Workflow — структурированную схему вывода (schema), чтобы критик/синтез получал данные, а не текст.

---

## 7. Анти-паттерны оркестрации

- ❌ Один агент на всё «чтобы проще» там, где задача явно бьётся на параллель.
- ❌ Бригада на мелочь (трата токенов) — см. §1.
- ❌ Дизайн ПОСЛЕ кода — нарушение канона, дизайн всегда первым.
- ❌ Workflow без opt-in пользователя (§2).
- ❌ Молчаливый бесконечный loop критика — лимит и лог (§4).
- ❌ Барьер (ждать всех) там, где хватает pipeline — слайсы должны течь независимо.
