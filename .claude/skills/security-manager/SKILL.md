# Security Manager — автономный red/blue оркестратор

Аналог `product-manager`, но для безопасности. PM подбирает скиллы и передаёт
их тебе; **security-manager подбирает И сам исполняет атаку/защиту волнами
агентов, авто-чинит найденное и пишет отчёт.** Работает автономно — Гриша не
подтверждает шаги (он сам сказал: «я в безопасности не разбираюсь, смысла
подтверждать нет»).

> **Authorized-use-only.** Этот скилл запускается ТОЛЬКО против проектов Гриши
> (его код, его серверы). Red-агенты ищут реальные уязвимости и строят
> эксплойт-цепочки — это законно исключительно на собственных системах. Никогда
> не наводи его на чужую инфраструктуру.

## Когда запускать / когда НЕ запускать

Запускай, когда Гриша просит проверить/взломать/защитить **свой** сервис, API,
бота, мозг, mini-app — одним из триггеров из `description`, или явно зовёт
`security-manager`.

НЕ запускай (перенаправь):
- быстрый чек одного файла / текущего диффа → `security-review`;
- общее качество кода (не безопасность) → `code-review` / `eng-code-review-and-quality`;
- «подбери скиллы для задачи» вообще (не про безопасность) → `product-manager`.

## Операционные правила (зафиксировано Гришей)

1. **Автономно, без гейтов.** Не спрашивай подтверждения между фазами. Показывай
   прогресс (`log`) и иди дальше. Останавливайся только если поднят реально
   разрушительный вопрос (напр. фикс требует необратимого действия — удаление
   данных, ротация боевого секрета) — тогда спроси текстом.
2. **Фиксы — авто, прямо в коде (вариант C).** Blue не «предлагает дифф» — он
   реально правит файлы. НО каждый авто-фикс обязан пройти **guard** (см. ниже).
3. **Между волнами пауза не нужна** — фиксы волны 1 применяются, затем сразу
   стартует волна 2.
4. **Отчёт** → `docs/security/AUDIT-<дата>.md` в самом проекте + короткий свод в
   чат. (Даты/время бери из окружения — в Workflow-скрипте `Date.now()` недоступен.)

### Auto-fix guard (защита от слепого фикса) — ОБЯЗАТЕЛЕН
Каждый фикс применяется оркестратором (тобой в главном цикле) **последовательно**,
не параллельно (иначе гонки по одним файлам). На каждый фикс:
- применил дифф → прогнал сборку/линт/тесты проекта (или превью-верификацию, если
  проект previewable);
- дыра действительно закрыта (перезапусти verify-агента на этом векторе);
- если фикс **ломает сборку/тесты или не закрывает дыру → откат** (`git checkout`
  файла), дыра идёт в отчёт как `manual-review-required`.
Никогда не оставляй проект в несобираемом состоянии.

## Пять фаз

### Фаза 0 — Scoping (понять задачу + код)
1. Вытащи из запроса **главный фокус** — что именно просят проверить.
2. Изучи архитектуру сам (Read/Grep/Glob, при нужде агент `Explore`): стек, точки
   входа, auth-флоу (Google/Firebase/OAuth/JWT/сессии), API-поверхность,
   загрузка/обработка файлов, `.env`/секреты, внешние интеграции, границы доверия.
3. Построй **attack-surface map**: список областей + для каждой — чем рискует.
4. Фокус главный, но **разрешено расширять**: жирную дыру вне запроса добавляй в
   карту с пометкой `bonus (вне основного фокуса)`.

### Фаза 1 — Routing (подбор sec-* скиллов, механика PM)
Открой `references/skill-routing-map.md`. Для каждой области карты подбери
конкретный `sec-*` скилл-плейбук (OAuth → `sec-testing-oauth2-implementation-flaws`,
Docker → `sec-hardening-docker-*`, загрузка по URL → `sec-performing-blind-ssrf-exploitation`
и т.д.). Результат — список **векторов**: `{id, area, file(s), sec_skill, hypothesis}`.
Это вход для red-агентов. Кратко залогируй карту + подобранные скиллы в чат.

### Фаза 2 — ВОЛНА 1: breadth, каждый сам за себя
Запусти **Workflow** по скелету `references/workflow-skeleton.js` → `wave1`.
- **Red 10–30** (по числу векторов, но целься в диапазон): каждый агент —
  отдельный «разработчик-хакер», работает изолированно над СВОИМ вектором,
  вооружён своим `sec-` плейбуком, ищет одну конкретную дыру в реальном коде.
  Возвращает `FINDING` (`файл:строка` + сценарий эксплуатации + severity).
- **Blue 3–7**: `verify` (адверсариально подтверждают/режут false-positive) и
  `fix-design` (готовят дифф). Работают в том же Workflow как pipeline-стадия.
- Выход волны 1 = **каталог подтверждённых дыр** + предложенные диффы.

Промпты и JSON-схемы — в `references/agent-roles.md`.

**Между волнами (ты, главный цикл):** применяй фиксы через Auto-fix guard
(последовательно, с тестами). Сохрани список закрытых / откачённых / оставшихся.

### Фаза 3 — ВОЛНА 2: depth, агенты работают СООБЩА (attack-graph)
Запусти **отдельный Workflow** → `wave2`. Смысл — не новые области и не
перепроверка своих фиксов, а **смена режима координации**: агенты объединяют
оставшиеся дыры в цепочки.
- Общая **war-board / attack-graph**: узлы = дыры («города»), рёбра = эксплойт-
  переходы («дороги»). Стартовые узлы — оставшиеся/частично закрытые дыры волны 1.
- **Red 10–18** работают **раундами**: каждый видит текущий граф, предлагает
  ребро/маршрут («A+C → дойду до X»), это его «реплика в обсуждении». Барьер
  собирает предложения, blue-verify подтверждает реалистичность ребра → валидные
  добавляются на доску. Следующий раунд все видят обновлённый граф (включая чужие
  дороги) и тянут дальше. Так реализуется «я нашёл — давайте вместе доломаем».
- Цель — сквозная **attack-path** от входа до критичного актива (данные / RCE /
  захват аккаунта). Как только путь найден — **Blue 3–5** ищут **choke-point**
  (min-cut: одно место, разрыв которого рвёт ВСЕ дороги к цели).
- Loop-until-dry: раунды, пока N раундов подряд не дают новых рёбер, или упёрлись
  в токен-бюджет.

**После волны 2 (ты):** авто-фикс choke-points через тот же Auto-fix guard —
это самые ценные фиксы (одним махом рвут целые цепочки).

### Фаза 4 — Synthesis (отчёт)
Собери `docs/security/AUDIT-<дата>.md`:
- Executive summary: сколько дыр, сколько закрыто авто, сколько на ручную, найдены
  ли сквозные attack-paths.
- Волна 1: таблица дыр (severity · файл:строка · статус fixed/rolled-back/manual · OWASP).
- Волна 2: найденные цепочки (дороги между городами) + применённые choke-point фиксы.
- Остаточный риск + рекомендации по `manual-review-required`.
Короткий свод — в чат.

## Бюджет агентов и потолки
- Каждая волна = **отдельный запуск Workflow** (волна1 ≤ ~37, волна2 ≤ ~23 — обе
  под потолком 50 из памяти `feedback_agent_cap_50`).
- Движок сам крутит ~10–14 одновременно, лишних ставит в очередь — все отработают.
- Если сессия режет размер (гайдлайн medium ≈ 15) — не блокируйся: работай тем
  числом, что даёт движок, диапазоны выше — это «цель, до».
- Red-агенты и verify — **read-only** (не правят файлы, безопасно параллелить).
  Правки применяет только оркестратор, последовательно.

## Файлы-референсы
- `references/skill-routing-map.md` — признак архитектуры → какой `sec-*` скилл.
- `references/agent-roles.md` — промпт-шаблоны red/blue (обе волны) + JSON-схемы находок.
- `references/workflow-skeleton.js` — готовые скелеты Workflow `wave1` и `wave2`,
  адаптируй под конкретный проект (векторы, цель, размеры волн).
